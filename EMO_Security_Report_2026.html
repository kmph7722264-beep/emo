三、本次已完成修正項目

A-2　HMAC 簽章密鑰隨機源升級

風險說明：原始碼使用 Math.random() 產生 256-bit 簽章密鑰，V8 引擎的 Math.random() 僅具備 64-bit 狀態（約 48-bit 有效熵），存在密鑰可預測風險，攻擊者若能推斷密鑰，可偽造問卷 token。

修正方式：改用 Google Apps Script 原生的 Utilities.getUuid()（UUID v4）呼叫兩次，取得 244-bit UUID 熵，轉為 base64url 後存入 Script Property。

// 修正前（不安全）
const bytes = [];
for (let i = 0; i < 32; i++) bytes.push(Math.floor(Math.random() * 256));

// 修正後（安全）
const rawBytes = (Utilities.getUuid() + Utilities.getUuid())
  .replace(/-/g, '').match(/.{2}/g).map(h => parseInt(h, 16));
key = Utilities.base64EncodeWebSafe(rawBytes).replace(/=+$/, '');
注意：若 Script Property SURVEY_SIGNING_KEY 已存在，不會重新生成；僅影響首次設定或手動刪除屬性後的下一次呼叫。

A-3　管理員 PIN 暴力破解防護

風險說明：ADMIN_REVEAL_PIN 為 4–8 位數字，無連線次數限制，攻擊者可以 1 秒數百次速率暴力破解。

修正方式：新增 checkAndRecordPinAttempt_(userId, inputPin) 函數，以 Script Properties（key：PA_<userId>）追蹤失敗次數：

  • 連續 3 次錯誤 → 封鎖 1 分鐘，回傳 HTTP 200 + { ok: false, error: "PIN 嘗試次數過多，請 XX 秒後重試" }
  • 驗證成功 → 清除計數器
  • 封鎖判斷在 PIN 比對之前執行，防止 timing attack
// handleStats_ 整合前（無保護）
const revealPin = getAdminRevealPin_();
const pinOk = !!(revealPin && body.adminPin && String(body.adminPin) === revealPin);

// 整合後（有速率限制）
let pinOk = false;
if (body.adminPin) {
  try {
    pinOk = checkAndRecordPinAttempt_(userId, body.adminPin);
  } catch (e) {
    return json_({ ok: false, error: e.message });
  }
}

B-1　管理員查單強制稽核留存

風險說明：handleFindOrder_ 允許已登入管理員查閱任意訂單之完整個人資料（姓名、電話、單位），但未留存任何查詢紀錄，無法事後追溯。

修正方式：在 handleFindOrder_ 查詢成功與查詢失敗兩個分支均呼叫 logAdminAction_()，寫入 AuditLog 工作表：

// 查無訂單
logAdminAction_(userId, 'findOrder', orderNo, {}, '找不到訂單');

// 查到訂單（包含訂單日期）
logAdminAction_(userId, 'findOrder', orderNo,
  { date: formatDateCell_(found[COL.DATE]) }, 'ok');

AuditLog 記錄欄位：時間戳記、操作者 userId、操作者顯示名稱、動作代碼、目標訂單號、細節（JSON）、結果。

B-2　電話號碼遮罩強化（前後端一致）

四、待改進事項（P1–P2）

A-1　LINE IDToken 完整驗證 P0

現況：目前 verifyIdToken_ 呼叫 LINE Verify API 驗證 ID Token，但未額外驗證 JWT 簽章（RS256），且若 sub（userId）為空字串時仍可繼續流程。

建議修正：

  • 驗證回傳 sub 非空，否則拋出例外
  • 現場點餐（walkin）路徑封鎖空 userId 進入
  • 考慮加入 nonce 參數（LIFF 前端 liff.getIDToken(nonce) ↔ 後端比對）防止 token 重放
// 建議加入 sub 非空檢查
const sub = JSON.parse(res.getContentText()).sub;
if (!sub) throw new Error('LINE token 驗證失敗：userId 為空');
return sub;

A-4　CORS 來源驗證強化 P0

現況：checkOrigin_ 在無法取得 Origin header 時（GAS 架構限制）對敏感 action 仍放行，等同無來源檢查。

建議修正：要求 LIFF 前端在 POST body 加入 origin 欄位（由 window.location.origin 填入），後端比對 body.origin + header.Origin 雙重驗證。

B-3　stats API 姓名明文回傳 P1

現況：handleStats_ 在未提供 adminPin 時已遮罩電話，但 name 欄位仍以明文回傳至前端 JSON。

建議修正：在 handleStats_ 回傳的 orders 陣列中，以 maskName_() 遮罩姓名（規則：保留首末字，中間以 * 取代）；或與 pinOk 條件並行——未解鎖時遮罩，解鎖時顯示明文。

B-4　LINE userId 長期保存 P1

現況：Orders 工作表存有使用者 LINE userId，系統設有 autoAnonymizeOldRecords() 函數（每月 1 日清除超過一年記錄的姓名/電話/userId），但需確認定時觸發器是否已在 GAS 控制台啟用。

建議動作：請至 GAS 主控台 → 觸發器（Triggers），確認 autoAnonymizeOldRecords 存在且設定為「每月執行」。若不存在，執行一次 setupAnonymizeTrigger()。

⚠️ 法規依據：個人資料保護法第 11 條規定「個人資料蒐集之特定目的消失或期限屆滿時，應主動或依當事人之請求，刪除、停止處理或利用該個人資料」。建議保留期限不超過 1 年，並訂定書面銷毀記錄。

B-5　問卷資料可識別個人 P2

現況：Survey 工作表 USER_ID 欄位直接儲存 LINE userId（明文），可與 Orders 表交叉比對還原個人身份。

建議修正：儲存 SHA-256(userId + SURVEY_SIGNING_KEY) 的截斷雜湊（前 16 bytes），既能防重複填答，又無法反推 userId。
