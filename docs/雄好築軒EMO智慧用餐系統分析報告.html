系統定位

雄好築軒智慧用餐系統是一套專為警政單位（雄好築軒）設計的 LINE 內嵌訂餐平台。使用者透過 LINE App 開啟 LIFF 頁面完成訂餐、查單、領餐，管理員透過同一介面管理菜單、統計出餐、標記領取。

系統以「低成本、零伺服器」為核心設計原則：前端部署於 GitHub Pages（免費靜態主機），後端以 Google Apps Script 搭配 Google Sheets 作為資料庫，無需月費主機費用。

由於服務對象為警政人員，系統涉及個人資料（姓名、警用電話、LINE userId）與業務資料（訂餐紀錄、用餐習慣），資通安全應列為與功能並重的設計要素。

四、資通安全評估

本節依據 OWASP Top 10、個人資料保護法及政府資通安全管理法相關要求，針對系統現況進行評估。系統雖屬內部服務，但涉及警政人員個人資料，且後端 API 端點為公開 URL，應予嚴肅對待。

4.1 身份驗證與存取控制

高
GAS API 端點為公開 URL，無來源白名單
Google Apps Script 部署後的 exec URL 為完全公開連結，不限制呼叫來源。任何人只要從前端 HTML 原始碼取得此 URL，即可直接呼叫 API，無需透過 LINE LIFF。 雖然後端依賴 LINE ID Token 驗證身份，若 Token 驗證流程存在缺陷，或攻擊者取得有效 Token，即可在 LINE App 外進行惡意操作（大量假訂單、資料探測）。
設定 GAS 的「Who has access」為「Only myself」並搭配 Service Account，或在 GAS 內檢查 Origin / Referer header 是否來自合法網域（有限效果但增加門檻）。長期建議加入請求頻率限制（Rate Limiting）。
高
管理員白名單無時效機制，離職人員可能保留存取權
管理員身份以 LINE userId 靜態儲存於 Google Sheets「Admins」工作表，無有效期欄位。若管理員調職、離職或手機遺失，其 LINE userId 除非手動刪除，否則永久保有管理員權限，可查看全體訂餐紀錄、取消他人訂單、修改菜單。
Admins 工作表增加「有效期限」欄位（如 2026-12-31），GAS 驗證時額外檢查日期；同時建立定期稽核流程（每季清查一次），並記錄新增/移除管理員的操作。
中
LINE ID Token 未在後端進行完整 JWT 簽名驗證
LINE ID Token 是一個 JWT，正確的驗證流程應包含：向 LINE Platform API 驗證 Token 簽名、檢查 iss（必須為 https://access.line.me）、aud（必須為本系統 Channel ID）及 exp（過期時間）。若 GAS 僅以 Token 解析姓名/userId 而未完整驗證，可能遭偽造 Token 攻擊。
GAS 應呼叫 LINE Verify API（https://api.line.me/oauth2/v2.1/verify）驗證每個 Token 的真實性，並確認 client_id 符合本系統的 Channel ID。
中
現場點餐（Walkin）模式缺乏後端時段強制驗證
現場點餐時段限制（早餐 08:00 前、中餐 12:30 前、晚餐 17:30 前結單，結單後 10 分鐘接受現場下單）目前僅由前端顯示提示，後端並未拒絕超時的現場訂單。惡意使用者可在截止後繞過前端限制，直接呼叫 API 送出現場訂單，影響出餐統計與公平性。
GAS 後端在接收 walkin=true 的訂單時，應比對伺服器時間與各餐時窗設定，超時直接回傳錯誤拒絕寫入。

4.2 個人資料保護

高
個人資料儲存於 Google Sheets，無加密、無存取日誌
訂單主表儲存姓名、警用電話、LINE userId（可對應至個人）、用餐習慣等個人識別資料（PII）。Google Sheets 本身未加密靜態資料，且若 Google 帳號遭入侵，所有訂餐資料將全數外洩。此外，Sheets 的存取紀錄（誰在何時查看了工作表）預設未啟用，難以事後稽核。
(1) 限制 Google Sheets 共用範圍（僅限特定 Google 帳號/群組可存取，關閉「連結共用」）； (2) 啟用 Google Workspace 的稽核日誌（需 Business 以上版本）； (3) 敏感欄位（電話）考慮以 GAS 側加密後儲存； (4) 定期匯出備份並刪除超過保存期限（建議 1 年）的舊資料。
高
未告知使用者個資蒐集範圍（缺乏隱私政策）
依個人資料保護法第 8 條，蒐集個人資料應明確告知蒐集目的、類別、利用範圍、保存期限及當事人權利。現行訂餐頁面無任何隱私說明或同意機制，使用者送出訂單即視為同意，不符合法規要求。
在訂餐頁面下方加入隱私說明（蒐集目的：訂餐服務；保存期限：1 年；不對外提供）及同意勾選框，或顯示指向完整隱私政策頁面的連結。
中
所有管理員可查看全體人員訂餐紀錄（無資料分級）
管理後台訂單明細顯示所有人的姓名、電話、用餐內容，所有具管理員身份者均可無限制查閱。在較大型組織中，應依「最小權限原則」限制資料存取範圍（例如：一線管理員僅能標領，不能查閱他人電話）。
設計角色分級：「超級管理員」（可查所有資料）vs「領餐人員」（僅能標領，電話欄位隱碼顯示 0912***678）。

4.3 輸入驗證與注入防護

中
備註欄位為自由文字，後端輸入驗證程度未知
訂餐頁面的「備註」欄位接受任意文字，若後端（GAS）將備註內容直接寫入 Sheets 或回傳顯示，可能存在 CSV 注入（=CMD() 類公式注入 Sheets）或 XSS 風險（若顯示於管理後台時未跳脫）。前端雖有 htmlEsc() 函式，但並非所有顯示路徑均完整套用。
(1) GAS 寫入 Sheets 時，對任何來自使用者的文字欄位在開頭加上單引號（強制為文字格式，防 CSV 注入）； (2) 前端所有動態插入 DOM 的文字一律使用 textContent 而非 innerHTML，或確保完整跳脫； (3) 備註欄位加上長度上限（如 200 字）防止超大 payload。
低
外部 CDN 資源未使用 SRI 驗證
頁面載入 LINE LIFF SDK（static.line-scdn.net）及 jsQR（cdn.jsdelivr.net）均未使用子資源完整性（Subresource Integrity, SRI）屬性。若 CDN 遭入侵並替換為惡意版本，使用者裝置將執行惡意腳本，且無任何防護。
對 jsQR 等第三方 CDN 腳本加入 integrity="sha384-..." 屬性；LINE LIFF SDK 因版本持續更新較難固定 Hash，可考慮自行下載至 repo 中托管。

4.4 傳輸安全

低
使用 text/plain 繞過 CORS preflight（設計上的安全妥協）
為避免 CORS 預檢請求（OPTIONS），POST 請求的 Content-Type 設為 text/plain;charset=utf-8。此做法雖有效且常見，但代表後端放棄了 Content-Type 嚴格驗證的第一道防線，任何網站均可對此 GAS 端點發出「簡單請求」（無需 CORS preflight），略微增加 CSRF 曝露面。
GAS 後端在處理請求時，額外驗證 Origin header（僅接受 github.io 與 liff.line.me）；同時確保所有敏感操作（訂單/標領）均需有效 LINE Token，杜絕未授權的跨站請求。
低
現場掃碼頁使用外部 CDN（jsQR），無法確保版本固定
scan.html 引用 cdn.jsdelivr.net/npm/jsqr@1.4.0，雖已固定版本號，但若 CDN 快取遭污染或 npm 套件被覆寫（供應鏈攻擊），仍有風險。
將 jsQR 的 JS 檔案下載至 liff/lib/jsqr.min.js 自行托管，避免 CDN 依賴，同時加入 SRI 驗證。

五、一般性待改進事項

5.1 已解決的問題（本次修正）

  • iOS UIPickerView 末項消失：中餐 C 餐在 iPhone 上無法顯示。已徹底重寫為 checkbox/radio 介面，完全避開原生選單限制。
  • 切換日期不更新菜單：已改用 wrapper div 穩定容器重建機制修正。
  • 錯誤倉庫問題：訂單頁 LIFF 指向舊 emo-ordering 倉庫，導致所有修正均無法生效。已統一指向 emo 倉庫。
  • LINE WebView 快取：根本原因為錯誤倉庫，已隨倉庫遷移解決，並加入 no-cache meta 標籤。

5.2 現存功能性待改進項目

1
單一 GAS 端點 — 無版本控制、無降級機制
若 GAS 部署出錯、配額耗盡（6 分鐘執行上限）或 Google 服務中斷，整個系統全面停擺，且無法快速回滾。
→ 維護兩個 GAS 部署（正式/備援），前端加入 fallback URL 設定。
2
無離線支援 / 網路失敗提示不足
fetch 失敗僅顯示紅字，無重試按鈕。在網路品質不穩的環境中使用者不知如何處理。
→ 加入「重試」按鈕，並以友善文字說明可能原因。
3
問卷與訂單系統未整合
survey.html 為獨立頁面，無法對應至特定訂單或菜色，難以自動化分析滿意度。
4
菜單需每日手動輸入
若管理員忘記輸入，使用者將看到「今日無此餐」。
→ 增加「複製上週同日菜單」快速功能。
5
無訂單修改功能
使用者送出後若要更改，只能聯絡管理員取消再重新下單，操作繁瑣。
→ 在「我的訂單」頁加入截止前的「修改」入口。
6
GitHub Pages 快取窗口（最長 20 分鐘）
CDN 快取加上 LINE WebView 快取，新版程式部署後最慢需等 20 分鐘生效。
→ 採用版本查詢字串（?v=20260525）強制繞過快取；重大更新時通知使用者清除 LINE 快取。

七、未來功能建議

7.1 短期建議（1–2 個月）

高優先

後端即時推播通知（出餐口管理者）

現場顧客或線上訂餐者到場掃 QR 領餐時，管理者電腦/手機出現大通知（5 秒停留），顯示用餐人資訊、自備餐具狀態。目前管理者須主動查詢，無法被動接收。

建議做法：GAS 標領時透過 LINE Messaging API 推送至管理員 LINE 帳號，並在管理後台使用 BroadcastChannel 同步多分頁顯示。

中優先

訂單修改功能（截止前）

使用者在截止時間前，可在「我的訂單」頁修改當日未截止餐別的選擇。GAS 新增 action=updateOrder，核查截止時間後覆寫欄位並推送 LINE 確認。

中優先

問卷與訂單掛鉤（滿意度分析）

標記領餐後，GAS 透過 LINE Messaging API 推送問卷連結（含訂單編號與日期參數），後端自動按日期、菜色分類統計滿意度，取代現行手動對照。

中優先

菜單快速複製（沿用上週同日）

管理後台加入「複製上週同日菜單」按鈕，減少每日重複輸入，降低忘記輸入的風險。

7.2 中期建議（3–6 個月）

一般

每週菜單批次設定

管理員一次輸入整週（5 天）菜單，系統自動套用對應日期，配合節假日標記（不提供餐點），避免下單失誤。

一般

訂單統計報表匯出（CSV）

管理後台加入「匯出當日/當月訂單 CSV」功能，方便結帳、報銷、統計，並可作為個資盤點依據。

一般

重複訂單防護

GAS 寫入時檢查 userId + date + meal 唯一性，防止同一使用者因網路重試造成重複訂餐。

一般

食材過敏 / 素食標記

菜單維護時標記各餐點的過敏原（花生、海鮮、麩質）及素食屬性，顯示於每日菜單頁，讓使用者訂餐前獲得充分資訊。

7.3 長期建議（6 個月以上）

長期

後端遷移至 Cloud Run / Firebase

當訂單量增大或需要 WebSocket 即時推播時，GAS 的 6 分鐘執行上限與無 Keep-Alive 特性將成為瓶頸。可評估遷移至 Google Cloud Run（按需收費）或 Firebase（免費額度充足）。

長期

多店點支援

若未來雄好築軒擴充地點，系統可透過 URL 參數 ?store= 加上 GAS 多工作表支援，擴展為多店點共用同一套前端程式碼。

八、建議優先順序與實作時程

第 1 週（立即）— 資安合規
  • 🔴 加入隱私說明與同意告知（個資法）
  • 🔴 限制 Google Sheets 共用範圍（關閉連結共用）
  • 🔴 GAS 後端完整驗證 LINE ID Token
  • 🔴 後端強制驗證現場點餐時段窗口
第 2–4 週 — 資安強化
  • 🟡 管理員白名單加入有效期限欄位
  • 🟡 備註欄位輸入驗證（長度限制 + CSV 注入防護）
  • 🟡 jsQR 改為自行托管並加入 SRI
  • 🟡 fetch 失敗加入「重試」按鈕
第 2 個月 — 功能補強
  • LINE Notify 推播（管理者被動接收標領通知）
  • 「修改訂單」功能（截止前，於我的訂單頁入口）
  • 問卷與訂單掛鉤（領餐後推問卷連結）
  • 菜單「複製上週同日」快速功能
第 3–6 個月 — 資料治理 + 功能擴充
  • 訂單資料保存期限機制（超過 1 年自動封存）
  • 管理員角色分級（超管 vs 領餐人員）
  • 每週菜單批次設定
  • 訂單報表匯出（CSV）
  • 食材過敏 / 素食標記
6 個月後 — 架構升級
  • API 請求頻率限制（Rate Limiting）
  • 評估後端擴展（Cloud Run / Firebase）
  • 多店點支援規劃
  • LINE LIFF SDK 版本升級評估

九、結論

雄好築軒智慧用餐系統以「零伺服器費用、LINE 生態整合」為核心，已實現完整的訂餐、菜單管理、領餐稽核流程，並於本次修正中解決 iOS 相容性、日期更新及錯誤倉庫等關鍵問題。

資通安全層面，系統目前最迫切的問題是個資法告知義務缺失及Google Sheets 個人資料存取控制不足，這兩項為法律合規要求，應列為最高優先、本週內完成。其次是後端 LINE Token 完整驗證及管理員帳號時效管理，屬技術安全強化，應於一個月內完成。

功能層面，最有價值的下一步是即時出餐通知（管理者被動接收提醒）及問卷與訂單掛鉤，投入相對小但對日常作業效率提升最為顯著。

整體而言，系統架構清晰、程式碼具可維護性，具備良好的擴充基礎。建議以「先補資安合規、再強化功能」的順序推進改進項目，確保在服務效率與資料安全之間取得平衡。
